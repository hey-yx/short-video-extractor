# 开发者指南

这份文档写给要在本仓库动手的人：跑起来改两行、给某个平台修解析、或者加一个新平台提 PR。README 讲接口和部署，`docs/详解-原理与使用.md` 讲原理和使用，这份讲怎么改代码。约定是硬的，解释在每条后面，改之前先看懂为什么。

## 1. 本地开发环境与命令

前置只有 [Bun](https://bun.sh) 1.2+（运行时兼包管理器，本仓库不用 Node）。浏览器兜底路径（抖音风控降级、小红书降级兜底）需要本机有 Chrome，Puppeteer 会自动管理；只走纯 HTTP 通道则不需要。

```bash
bun install              # 装依赖
bun dev                  # 开发服务（--watch 热重载），默认端口 7777
bun test                 # 全部单测，全离线 fixture 回归
bun run typecheck        # tsc --noEmit 类型检查
bun run format           # prettier 格式化 src 和 tests
bun run test:status      # 一条命令看全状态：格式 / 类型 / 单测 / 覆盖率 / CI
bun run build:binary     # 编译单二进制到 dist/sve
```

提交前把 `bun run typecheck` 和 `bun test` 跑绿是最低要求，`bun run test:status` 是给 CI 对齐用的总闸。路径别名 `@/*` 映射到 `src/*`（tsconfig 里配的），代码里统一用 `@/core/errors` 这种写法。

配置参照 `.env.example`。不配任何 env 也能跑：纯 HTTP 主通道不需要凭据，浏览器兜底会随风控自动启用。`DOUYIN_UIFID`（抖音 L2 签名通道）、`IG_GRAPHQL_DOC_ID`（Instagram GraphQL 口子）、`PROXY_SECRET`（/media 中转）这几个是可选增强，见 README 环境变量表。

## 3. 代码约定

### 3.1 平台层三条硬约束

`src/platforms/**` 里：

1. 不 import Elysia（不引 HTTP 框架）
2. 不读 env（配置一律从 `FetchCtx` 注入）
3. 不 console.log（日志走 `ctx.logger`）

加上接口契约（`types/platform.ts` 的注释原文）：`match()` 必须是纯函数，`fetch()` 是唯一允许 IO 的方法，`parse()` 必须是纯函数，同输入同输出。

为什么这么严：平台层是这个项目里变动最频繁的部分，平台改版、风控升级、字段挪位都发生在这里。约束把「平台逻辑」压成可以在测试里离线跑的纯函数，平台改版时的表现是单测先红，而不是线上悄悄返回空结果。不读 env 还有一个实际原因：同一份 adapter 代码要能在测试里喂任意配置（比如假的 uifid）而不用改环境。`platforms/**` 不 import Elysia 让平台包与 Web 框架解耦，框架换了平台层一行不动。

IO 只经两个口子：全局 `fetch()`（超时、取消靠传入的 `ctx.signal`）和 `ctx.browser` 注入的页面操作接口（`getDocumentHtml` / `interceptJson`，不暴露 puppeteer 类型）。需要出站代理的平台（海外）用 `src/core/fetch-proxy.ts` 的 `proxiedFetch`，代理值取 `ctx.proxyUrl`。

### 3.2 FetchCtx 注入

`FetchCtx`（定义在 `types/platform.ts`）是平台层拿外部世界的唯一通道：`signal`（取消）、`channel`（http 或 browser）、`logger`、`browser`、`proxyUrl`、`instagramDocId`、`douyinUifid`、`douyinTtwid`。

组装点在 `routes/parse.routes.ts`：routes 层读 env，把值填进 ctx，平台侧只读字段。所以新增一个「平台需要的配置项」的正确姿势是：`FetchCtx` 加可选字段，routes 层从 env 注入，平台层从 ctx 读，全程不碰 `process.env`。未配置时的行为由平台层给可懂报错（参考 Instagram 缺 `docId` 的 `CONFIG_MISSING`）或优雅降级（参考抖音缺 `uifid` 时由身份池自动铸造，没有浏览器能力才跳过 L2 直落浏览器兜底）。

### 3.3 错误码怎么加

错误码集中在 `src/core/errors.ts`，是一个封闭枚举 `ErrorCode` 加一张 `HTTP_STATUS` 映射表。业务代码只做一件事：`throw new AppError('CODE', '可读消息', { detail })`。响应信封和 HTTP 状态由路由层统一处理（`core/envelope.ts` 的 `fail()`），平台代码不构造响应。

加一个新错误码的步骤：

1. 在 `ErrorCode` 联合类型里加名字，选一个稳定、可归因的语义，别把「不知道哪坏了」做成新码（那是 `INTERNAL`）。
2. 在 `HTTP_STATUS` 表里配状态码。语义参考现有：客户端传错东西 400/422，内容问题 404/403，上游问题 502/504，风控 503。
3. 检查打点是否需要区分：`parse_total{code}` 会自动带上新码，无需额外接线。但要想清楚它和现有码的归因边界。

两个易混码的分界要守住：`RISK_CONTROL` 是风控拦截（平台在拒绝你），`UPSTREAM_CHANGED` 是口子或字段变了（平台改版了）。前者重试会加重风控，后者重试无意义要改代码。抖音 L1 风控归 `RISK_CONTROL`，L2 签名失效（403 或 200 空 body）归 `UPSTREAM_CHANGED`，错误码与打点都分开，就是为了运维时能区分「被堵」和「签名过期要重铸」。

### 3.4 指标怎么打

指标在 `src/infra/metrics.ts`，自写 Prometheus 文本格式渲染，三种类型：counter（`metrics.inc`，累加）、histogram（`metrics.observe`，耗时分布）、gauge（`metrics.setGauge`，直接设值，用于熔断这类状态量）。

打点习惯是给每个指标配一个语义化的 `recordX()` helper（如 `recordParse`、`recordChannelDowngrade`），业务代码调 helper 不直接摸 `metrics`。新增指标的步骤：

1. 在 `metrics.ts` 加 `recordXxx` helper。
2. 在 `render()` 里加对应的 `# HELP` / `# TYPE` 输出段和遍历输出（这个文件是手写渲染，不加段落指标不会出现在 /metrics 上）。
3. 命名对齐现状：`*_total` 是 counter，`*_ms` 是 histogram，状态量用 gauge。label 用 `platform`、`code`、`reason`、`from`/`to` 这些已有惯例。
4. 在 `prewarm()` 里预热一条 0 值（如果希望该指标在无数据时也出现在 /metrics 上，Prometheus 语义下空序列等于不存在）。

## 4. 加一个平台的完整步骤

以「你要加一个叫 foo 的平台」为例。先调研后动手：没有实测证据的字段路径就是猜的，猜的解析上线必坏。调研结论按现有格式补进 `docs/research/`（怎么发现的口子、请求配方、实测字段路径、踩过的坑），这既是 PR 的依据也是下次排错的资料。

**第 1 步，类型**：`src/types/platform.ts` 的 `Platform` 联合类型加 `'foo'`。

**第 2 步，域名表**：`src/platforms/hosts.ts` 的 `PLATFORM_HOSTS` 加 foo 的分享域和短链域。这张表是三件事的数据源：平台识别（registry.match）、SSRF 第一道闸（/media 白名单由它派生）、`/platforms` 自描述。域名用后缀匹配（`news.foo.com` 属于 `foo.com`），所以只列根域，短链域（如 `f.cn`）单列。

**第 3 步，适配器**：建 `src/platforms/foo/`，两个文件：

- `adapter.ts` 导出 `fooAdapter: PlatformAdapter`，实现四个方法：
  - `match(url)`：纯函数，从 URL 提平台内 ID 和 kind，短链返回 `needsResolve: true`；识别不了返回 null。
  - `resolve(url, ctx)`（可选）：短链展开，只解析一跳返回最终 URL，dispatch 会递归再 match（深度上限 3 防循环）。
  - `fetch(input, url, ctx)`：唯一允许 IO 的方法，返回可 JSON 序列化的 `RawPayload`（fixture 能录制回放的前提）。超时、取消一律用 `ctx.signal`。
  - `parse(raw, input)`：纯函数，把 RawPayload 变成 `ParseResult`，字段填不满没关系，但 `id`、`kind`、`assets` 必须准。
- `parse.ts` 放纯函数解析主体（从 adapter.ts 拆出来是为了测试直接 import）。

`capabilities` 如实声明（http / browser / tlsImpersonation / kinds），`description` 写清楚通道一句话，这两个会出现在 `/platforms` 自描述里。

**第 4 步，注册**：`src/bootstrap/app.ts` import 并 `register(fooAdapter)`，一行。

**第 5 步，配置（如需要）**：平台要的凭据或开关加到 `FetchCtx`，routes 层注入，参照 3.2。绝不让平台读 env。

**第 6 步，CDN 白名单（如走 /media 中转）**：`src/services/media-proxy.ts` 的 `CDN_HOSTS` 加 foo 的媒体 CDN 域（`PLATFORM_HOSTS` 只列分享域，直链在 CDN 域上）。

**第 7 步，fixture 与测试**：

- 录一份真实响应进 `tests/fixtures/foo/`。录制脚本参照 `scripts/record-tiktok-fixtures.ts`，脱敏原则照抄：字段名照实，URL 里一次性签名段打码但保持结构，统计类计数归零。
- `tests/unit/foo-match.test.ts`：URL 识别（各种分享链接形态、短链、不认的链接返回 null）。
- `tests/unit/foo-parse.test.ts`：fixture 回归，覆盖正常视频、图集、以及上游改版时的报错分支（parse 找不到关键字段时抛 `UPSTREAM_CHANGED`）。
- 取数链路有特殊行为（降级、重试、短链展开）的，加 routes 层测试，假 fetch 注入见第 5 节。

**第 8 步，自查**：`bun run typecheck && bun test && bun run test:status` 全绿。

**第 9 步，文档**：README「平台状态」表加一行，`docs/research/` 补调研记录，行为特殊的（绑 IP、需要代理）在 README 里写明。

Checklist 版（PR 前逐项打勾）：

```markdown
- [ ] docs/research/ 有实测调研记录（口子、配方、字段路径、坑）
- [ ] types/platform.ts 的 Platform 联合类型已加
- [ ] hosts.ts 的 PLATFORM_HOSTS 已加分享域与短链域
- [ ] platforms/foo/adapter.ts 四个方法齐全，capabilities 如实
- [ ] platforms/foo/parse.ts 纯函数，关键字段缺失抛 UPSTREAM_CHANGED
- [ ] bootstrap/app.ts 已注册
- [ ] 配置项走 FetchCtx 注入（如需要），平台层零 env
- [ ] media-proxy.ts CDN_HOSTS 已加（如走 /media）
- [ ] tests/fixtures/foo/ 有脱敏录制的 fixture
- [ ] match / parse 单测覆盖正常与异常分支
- [ ] bun run typecheck && bun test && bun run test:status 全绿
- [ ] README 平台状态表已更新
```

## 5. 测试怎么写

两条底线：全离线，全确定。CI 里没有网络也没有 Chrome，测试碰真网就会 flaky（时好时坏），所以所有上游都是假的，所有输入都是入库的 fixture。

**假上游注入**。接口层测试用 `createApp()` 拿应用实例，直接 `app.handle(new Request(...))`，不起端口。上游靠替换 `globalThis.fetch` 模拟，惯例是三件套（参照 `tests/routes/parse.routes.test.ts`）：

```ts
const realFetch = globalThis.fetch;

beforeEach(() => {
  // 默认 stub 成失败：任何用例都不许误打真实网络
  stubFetch({ unexpected: true });
  // 清单例状态：熔断、止血窗口、缓存，防止上个用例串味
  resetChannelPolicyForTests();
  parseCache.resetForTests();
});

afterAll(() => {
  globalThis.fetch = realFetch;   // 还原，测试文件之间不互相污染
});
```

stub 函数里按 URL 分支返回 fixture 内容；没预料到的 URL 返回 500 并让它在断言里露馅。另外两个细节：每个用例用独立 IP（`x-real-ip` 头递增），避开共享限流桶互相干扰；假 `aweme_id` 之类要互不重复，避开缓存串用例。

**fixture 回归**。`parse()` 是纯函数，测试就是把 `tests/fixtures/<platform>/` 里录好的 `RawPayload` 喂进去断言输出字段。fixture 是真实上游响应脱敏后的快照，平台改版时先改 fixture 再改 parse，diff 就是改版内容本身。断言写具体值（ID、标题、尺寸、URL 特征），别写「不为空」这种糊过去的断言。

**不打真网的约定**。`tests/probe-*.ts` 是手动探针（打真实链接验证通道活着），文件名不带 `.test`，`bun test` 不会自动执行，需要时 `bun tests/probe-xhs.ts` 单独跑。它们是维护工具不是测试，坏了不影响 CI。这条约定的收益在升级依赖、跑 CI、离线开发时兑现：`bun test` 在任何环境都是同样结果。

## 7. 维护手册

这个项目没有一劳永逸的通道：平台侧堵口子、换签名、改字段是常态，维护就是盯指标提前发现，而不是等用户报障。

**通道过期信号怎么看指标**。`curl http://<服务>:7777/metrics`，或直接看 Gatus 仪表盘（compose 起在 `http://<服务器>:8080`）：

| 信号 | 含义 | 动作 |
|---|---|---|
| `channel_downgrade_total{from="http",to="http-l2"}` 持续增长 | 抖音 L1 零签名口子被风控常态化，L2 在被消耗 | 观察为主；L2 也开始降级再动手 |
| `channel_downgrade_total{to="browser"}` 增长、响应里 `via` 大面积是 `browser` | 某平台 HTTP 通道整体退化，流量在吃浏览器兜底 | 读该平台 research 记录找新口子，兜底只是缓冲不是解法 |
| `parse_total{code="UPSTREAM_CHANGED"}` 突增 | 上游改版：字段挪位、口子变更、签名失效 | 对照 research 里记录的字段路径抓一份新 fixture，改 parse 让单测先红再修 |
| `parse_total{code="RISK_CONTROL"}` 突增、`channel_breaker_open{platform}` 长时间为 1 | 风控拦截，熔断粘性生效（该平台 60s 内固定走浏览器） | 先确认是不是自己请求太密；持续风控考虑换出口 IP 或开代理 |
| `upstream_error_total{reason}` 增长 | 上游超时或 5xx | 多为平台侧抖动，结合 `parse_duration_ms` 判断是变慢还是挂了 |
| `parse_duration_ms` 整体右移 | 上游变慢或代理变慢 | 检查出站代理链路（海外平台），或上游服务状况 |

**uifid 重铸入口**。抖音 L2 签名通道靠 `uifid`（一次性用浏览器铸造的访客身份）加 `x-secsdk-web-signature` 签名过风控。不配 `DOUYIN_UIFID` 时身份由 `platforms/douyin/uifid-pool.ts` 自动管理：有浏览器能力就自动铸造、池化复用、用废换新（铸造节流 60s 起、失败退避到 1h），运维基本不用管，指标看 `uifid_mint_total` / `uifid_retired_total`。显式配置 `DOUYIN_UIFID` 是固定身份模式，失效才需要手动重铸：失效信号是 L2 请求 403（`Sign Invalid` / `Uifid Not Found`）或 200 空 body，两者都归 `UPSTREAM_CHANGED`，同时 `channel_downgrade_total` 里 http-l2 到 browser 的降级会涨。重铸步骤是现成的复铸手册：`docs/research/01-douyin-tiktok-api.md` §12.2，一段 puppeteer 脚本从 douyin.com 抄 `UIFID_TEMP` cookie，连同当场的 `ttwid` 一起配到 `DOUYIN_UIFID` / `DOUYIN_TTWID`。两个值是同身份体系，同场带出的组合最稳。重铸前先确认不是配方本身变了：§12.4 记录过 a_bogus 从能用变毒参数的先例，改配方前按该节的 A/B 方法单变量验证。

**签名算法过期：换签名器，不改主仓**。上面重铸 uifid 治的是身份失效；如果是签名算法本身换了（bdms 升级，`x-secsdk-web-signature` 与服务端验算对不上），走签名器替换。签名怎么算不写死在 adapter 里，`core/signers.ts` 定义了 `SignerProvider` 接口（`signRequest` 算签名、`isAvailable` 自检、`mintTtwid` 铸访客 cookie），注册表按优先级选第一个可用的，默认实现是 `platforms/douyin/abogus-signer.ts`（abogus 库）。替换步骤：照 `SignerProvider` 写一个新实现（参考 `docs/research/01-douyin-tiktok-api.md` §12 的算法描述），在 `bootstrap/app.ts` 里 `registerSigner(newSigner, { priority: 10 })`，启动即生效；同名重复注册视为替换，方便重启式热加载。注册表空时请求构造会回落内置默认，所以新实现写坏了也不会比现在更糟。验证换没换成功：`curl /platforms` 看 douyin 条目下的 `signers`（name / version / available），或代码里 `activeSignerInfo()`；新签名先真机单变量验一次（§12.4 的 A/B 方法），别带着整套假设上线。

**其他例行事项**：

- 直链会过期（`expiresAt` 语义），缓存和 /media 中转都按它重取，这不是故障。
- 平台改版修完后重新录 fixture（脱敏原则见第 4 节第 7 步），旧 fixture 别留着骗自己。
- 升级 Bun 或依赖后跑 `bun run test:status` 对齐 CI。
- 偶尔跑 `docker image prune` 清构建缓存，镜像验收看 `docs/image-build-notes.md`。
