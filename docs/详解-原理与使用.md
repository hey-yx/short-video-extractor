# 短视频去水印解析：原理、用法与维护

拿一条抖音或小红书的分享链接，换成能直接下载的无水印视频地址，这就是 short-video-extractor 在干的事。九个平台（抖音、小红书、快手、B 站、微博、X、YouTube、Instagram、TikTok）接在同一套接口上，返回同样结构的结果。这篇讲两件事：各平台的关卡到底难在哪、项目怎么过；以及拿它跑起来、配好、出问题怎么排。

## 解析链接这件事，难的不是解析

分享链接打开是个网页，视频文件并不在网页里。它藏在网页背后的接口返回里，而且平台不欢迎你直接拿走：下载的版本带水印，接口有各种检查，查得严的时候请求直接被拒。要拿到干净的直链，本质上只回答一个问题：怎么让平台把这个请求当成一次正常访问放过去。

平台的检查手段就那么几种，后面反复会出现，先用日常话交代清楚。

签名是请求上盖的章。浏览器请求接口时，客户端按一套算法把请求内容算出一个值，附在 URL 或请求头里，服务端验算一遍，对不上就拒。算法藏在平台自己的 JS 里，而且随版本升级会换。这是各家接口里最难对付的部分。

风控是平台对「你是不是真人」的判断。它看身份凭证（cookie，相当于一张访客证）、请求指纹（参数和请求头像不像真浏览器），还有行为（同一个 IP 短时间撞太多次，就是机器人特征）。被盯上的结果通常是 403，也有更阴的一种：返回 200 但正文是空的，看起来成功，其实什么都没给。后面会看到，这个「假成功」在实测里是真实存在的。

登录墙最简单粗暴：内容要登录才给看，匿名请求直接被拒。

直链是平台 CDN 上视频文件的真实地址，拿到就能下载。它一般有时效，几小时到几天不等，过期就重新解析一次。

## 九个平台，各怎么过关

| 平台 | 关卡 | 项目的过法 | 需要注意 |
|---|---|---|---|
| 抖音 | 签名 + 风控 | 三级降级链：零签名口子 → 自算签名 → 浏览器兜底 | 直链不绑 IP，好下载 |
| 小红书 | 请求头伪装 + 登录墙 + IP 风控 | 请求头三件套放行，风控时自动降级浏览器 | 风控错误如实报 503 |
| 快手 | 分享页取数 | 短链展开取 photoId，拿分享页里的初始数据 | 零 cookie |
| B 站 | 官方接口多一层鉴权 | view + playurl 两步，带游客身份 | DASH 音视频分离，下载端要自己合成 |
| 微博 | 接口分档 | 匿名 JSON 接口 + 视频直链页换算 | 1080P 档位藏在另一个接口里 |
| X/Twitter | 接口签名 | 走免签名的公开接口口子 | 直链不校验出口 IP |
| YouTube | PO Token 要求 + 直链绑 IP | innertube 接口换 client 策略绕开 | 直链绑解析出口 IP，约 6 小时过期，必须走服务端中转 |
| Instagram | 登录墙 | 匿名 GraphQL 口子 | 需要配一个会轮换的 doc_id |
| TikTok | 签名 | 走公开中转接口 | 解析出站需要代理 |

拿几个有代表性的展开说。

小红书的门槛在请求头。同样的接口，光秃秃的脚本请求会被拒，把 User-Agent、Accept、Accept-Language 三行装成浏览器就放行了。项目里小红书是纯 HTTP 主通道，遇到登录墙或 IP 风控（错误码 300012）时才降级浏览器，而且风控和改版在报错上分开：风控报风控，不要冒充「接口变了」。

YouTube 的麻烦在直链。它的视频地址绑解析那一刻的出口 IP，也就是说解析和下载必须从同一个出口走，而且地址大约 6 小时过期。所以 YouTube 的直链不能像其他平台那样发给客户端直接下，要经本服务的 `/media` 中转转发，中转和解析配同一个代理出口。Instagram 反过来，它的口子要配一个 `IG_GRAPHQL_DOC_ID`（平台前端接口的查询模板 ID，会轮换），配置了就能免登录免 cookie 解析。

快手、B 站、微博、X、TikTok 这几家相对省事，各有公开或半公开的接口能拿到数据，纯 HTTP 就能过，难点藏在细节里：B 站的清晰度映射、微博的档位接口差异、快手短链到 photoId 的取数路径。这些细节都在各平台的 adapter 里封装好了，调用方不用关心。

## 抖音的三层：项目的思路看它就够了

抖音是九家里最难的，也是项目思路最完整的体现：不指望一条路走到黑，把「更稳但更重」的方案排在后面当退路。

第一层是一个零签名的口子。抖音网页版的官方播放器要给自己加载视频，它用的 detail 接口没有签名检查。项目直接调这个接口，请求最快最轻，这就是默认主通道。问题是这个口子是「利用来的」，哪天官方把检查加上就没了，所以它随时可能被堵。

第二层是自己算章。正常浏览器访问抖音网页时，请求上带两样东西：一个访客身份 uifid（cookie，服务端发的，相当于进门登记后的访客证），和一个请求头签名 x-secsdk-web-signature（把 URL、时间戳和身份一起算出来的章）。项目用开源的 `abogus` 库自己算这个章，逐字节对过真机浏览器发的请求，签名完全一致。uifid 需要一次性用浏览器铸造（开一次抖音页面，等它的 JS 挑战跑完，cookie 里就会出现），铸好存进配置长期复用。

第二层里有个值得讲的实测故事。调研阶段按公开资料写的配方是四件套：签名、uifid、ttwid，再加一个叫 a_bogus 的查询参数。真机 A/B 测试发现 a_bogus 是毒参数：带上它（三种构造方式都试了）稳定被风控引擎用「200 + 空 body」静默拒绝，去掉它就 200 全量返回。msToken 这类参数塞进查询同样触发拒绝。真正把门的只有 uifid 和那个请求头签名。这件事的教训是这类配方必须真机验证，公开资料会过期，而且过期得很安静。

第三层是浏览器兜底。直接开一个真浏览器加载作品页，截获页面自己发出的接口请求，把浏览器拿到的 JSON 当结果。这一层最稳（浏览器能过所有检查，包括 JS 挑战），但最重：慢、吃内存，还有并发限制。所以它是退路不是主路。

三层怎么串：默认走第一层；第一层被风控（403）就试第二层；第二层也失效（403 或 200 空 body）才进浏览器。返回结果里 `via` 字段如实标注走的是哪条：`http`（第一层）、`http-l2`（第二层）、`browser`（第三层）。

两种失效在报错上是分开的，这直接决定你该做什么：第一层被堵报 `RISK_CONTROL`，说明口子收紧了，靠后两层顶着就行；第二层失效报 `UPSTREAM_CHANGED`，多半是签名过期或 uifid 失效，重铸一次 uifid 就能修好（步骤在 `docs/research/01-douyin-tiktok-api.md` §12.2）。

## 风控之后，系统自动做的事

被风控时最不该做的就是反复重试。风控看行为，越撞越像机器人，重试是在加重自己的负面画像。项目把这条原则落成了三个机制。

熔断粘性管「别再走死路」。某通道连续两次命中风控后，60 秒内不再试它，固定走下一级通道（省掉每个请求先吃一次 403 的延迟），到点放一个请求回去试探，试探成功就切回来。

风控止血管「没有退路时别空转」。如果没配浏览器兜底，风控命中后该平台进入 45 秒窗口，窗口内的请求直接返回 503，不再打上游。已缓存的结果照常返回，不受影响。

缓存管「少打上游」。解析结果带直链过期时间，在过期前的重复请求直接返回缓存，一个热门视频只打一次上游。同一条链接的并发请求还会合并成一次解析，不会互相重复撞上游。

## 跑起来：从零到第一次解析

前置是装好 [Bun](https://bun.sh)（1.2 以上）。然后：

```bash
git clone https://github.com/hey-yx/short-video-extractor.git
cd short-video-extractor
bun install
bun dev
```

服务默认监听 7777 端口。拿一条真链接试：

```bash
curl -X POST http://127.0.0.1:7777/parse \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://v.douyin.com/xxxxxxx/"}'
```

不想装环境就 Docker：

```bash
docker compose up -d
```

返回是统一信封，成功长这样：

```json
{
  "success": true,
  "data": {
    "platform": "douyin",
    "title": "视频标题",
    "author": { "name": "作者" },
    "kind": "video",
    "assets": [
      {
        "url": "https://...cdn.../play/xxxx.mp4",
        "width": 1080,
        "height": 1920,
        "durationMs": 15000,
        "variants": [ ... ]
      }
    ],
    "expiresAt": 1761000000,
    "via": "http"
  }
}
```

`data.assets[].url` 就是无水印直链，直接下载即可。几个字段值得知道：`expiresAt` 是这条直链的过期时间（Unix 秒），过期重新解析；`variants` 是同一资源的其他清晰度档位（抖音带 540p 到原片四档）；`via` 是走的哪条通道，排查问题时先看它。

图集（小红书图文、抖音图集）的 assets 里是多张图片；B 站 DASH 流会把音频放在 `audioUrl` 里，下载端要分别拉视频和音频自己合成。

完整的真实响应样例、各场景怎么取字段、出错怎么处置见 [`调用案例.md`](调用案例.md)。

## 配置怎么选

全部配置走环境变量，`.env.example` 里有一份带注释的模板。逐个说怎么选。

| 变量 | 默认 | 怎么选 |
|---|---|---|
| `PORT` | 7777 | 监听端口 |
| `BROWSER_FALLBACK` | on | 设 `off` 全平台纯 HTTP，风控如实 503，省 400-600 MB 内存 |
| `DOUYIN_UIFID` | 未配置 | 配了抖音才启用第二层签名通道；不配则风控直接落浏览器 |
| `DOUYIN_TTWID` | 未配置 | 可选，和 uifid 同一次铸造带出最稳；不配会自动注册一个 |
| `PROXY_SECRET` | 未配置 | 配了才启用 `/media` 中转；YouTube 用户必须配 |
| `PROXY_<PLATFORM>` / `HTTPS_PROXY` | 未配置 | 海外平台出站代理（如 `PROXY_YOUTUBE`） |
| `IG_GRAPHQL_DOC_ID` | 未配置 | Instagram 解析必需，平台轮换后要跟着换 |

资源和稳定性的取舍主要在 `BROWSER_FALLBACK`。开着它，风控时有浏览器兜底，最稳，代价是 Chrome 常驻内存 400-600 MB；关掉它，服务纯 HTTP、轻，但被风控时如实报 503 等窗口过去。小机器或者不在乎偶发 503 的场景就关。注意这个开关生效方式是读环境变量，容器部署改完要重启容器才生效。

`DOUYIN_UIFID` 值得配，它让抖音的第二层可用，被风控时就不用每次去开浏览器。铸造方法：一次性开个浏览器访问 `douyin.com/jingxuan`，等 8 秒左右让它的 JS 挑战跑完，在 cookie 里找 `UIFID_TEMP`（一串 150-160 字符的十六进制），连同同场带出的 `ttwid` 一起填进环境变量。完整步骤和验证方法在 `docs/research/01-douyin-tiktok-api.md` §12.2。这个值可以长期用，报签名过期（`Sign Invalid` / `Uifid Not Found`）时重铸一次即可。

## API 之外的接口

`/parse` 之外还有几个，运维时用得上。

`GET /media?u=&exp=&sig=` 是流式中转（配置 `PROXY_SECRET` 后启用）。sig 是 HMAC 签名，有效期 600 秒，防外链盗用。它的用途一是 YouTube 这类直链绑 IP 的场景，二是直链带 Referer 限制时替客户端挡在前面。并发上限 2，大文件转发不吃内存（流式透传）。不配就是 501，直链主路径不受影响。

`GET /health`、`GET /ready` 给探活用；`GET /platforms` 列出各平台能力声明；`GET /metrics` 是 Prometheus 格式的指标，里面 `channel_breaker_open{platform}` 看熔断是否开着，`channel_downgrade_total` 看降级频次，跑一阵子就能看出哪条通道在被消耗。

限流是按 IP 的令牌桶，过于频繁返回 429。错误响应也是统一信封，`error.code` 是机器可判的错误码。

## 出问题了，先看错误码

| 错误码 | 意思 | 该怎么办 |
|---|---|---|
| `RISK_CONTROL` (503) | 被平台风控了 | 等窗口过去；抖音配了 uifid 就会自动走第二层；持续出现考虑配代理或浏览器兜底 |
| `UPSTREAM_CHANGED` (502) | 接口变了或签名过期 | 抖音场景多半是重铸 uifid；其他平台要更新解析逻辑 |
| `CONTENT_NOT_FOUND` (404) | 内容不存在或已删 | 无解，链接本身的问题 |
| `CONTENT_RESTRICTED` (403) | 内容受限（仅自己可见等） | 无解，权限问题 |
| `UPSTREAM_TIMEOUT` (504) | 上游超时 | 自动重试过一次仍失败就是真慢，稍后再试 |
| `RATE_LIMITED` (429) | 本服务限流 | 降请求频率 |
| `MEDIA_PROXY_DISABLED` (501) | /media 未启用 | 配置 `PROXY_SECRET` |

拿到结果但下载不了，先看三件事：直链过没过期（`expiresAt`）、`via` 是不是 `browser`（浏览器通道的直链有时效更短）、是不是 YouTube（必须走 `/media`）。

## 想改代码的话

代码分四层，职责是分开的：`routes/` 管 HTTP 接口和限流，`services/` 管编排（缓存、重试、降级调度），`platforms/` 是九个平台各自的解析逻辑，`infra/` 管日志、指标、浏览器网关这些基础设施。请求流程是：识别平台 → 查缓存 → 展开短链 → 取数据 → 纯函数解析 → 统一信封返回。

加一个平台的成本很低：`platforms/` 下加个目录，`bootstrap/app.ts` 注册一行。平台层有三条约束保证可测性：不引 HTTP 框架、不直接读环境变量（配置从 `FetchCtx` 注入）、`parse()` 是纯函数。所以平台解析逻辑全部可以用固定的假数据离线测试，平台改版时的表现是「单测先红」，而不是线上悄悄返回空结果。测试跑 `bun run test`，类型检查 `bun run typecheck`。

## 边界和维护预期

几件要提前知道的事。

直链不是永久地址。它由平台 CDN 下发，带过期时间，做下载器或收藏类功能时要按 `expiresAt` 处理过期重解析。

没有一劳永逸的通道。抖音第一层是利用口子，随时可能被堵；第二层的签名算法会随平台升级过期；第三层最稳但最重。其他平台同理。这类项目的常态是持续维护：跑一阵子看指标，某条通道降级次数涨了就说明它在被消耗，提前准备而不是等它全挂。

本项目只做解析，不存视频、不转码、不搬流量。返回的是平台自己 CDN 上的公开直链，下载流量直接在客户端和平台 CDN 之间走。唯一的例外是 `/media` 中转场景（YouTube），那是转发不是存储。

排错材料都在仓库里：`docs/research/` 是各平台的实测调研记录（怎么发现的口子、配方、踩过的坑），`README.md` 是接口和部署速查，出了问题先查错误码表，再查对应平台的 research 记录。
